2. COGNITO MISMATCH (tracked concern C8; nothing applied)
- Fonts:
  - The web uses IBM Plex Sans + Noto Sans Thai (fonts.css, P2a).
  - The AWS classic hosted UI allow-list has no font-family property at all [V:WebFetch docs.aws.amazon.com hosted-ui-classic-branding]. Cognito therefore renders in AWS's default stack; the exact family is [A] (likely a Helvetica/Arial-type system stack), and Thai falls back to the OS font.
  - The wordmark in the logo is outlined Inter, so it is consistent wherever it appears.
  - Classic branding cannot fix the font. Only Managed Login (v2) branding could, and that is a domain/branding-version change that needs AWS approval and possibly re-testing auth.
- Properties AWS does not list for these classes [V:AWS doc]:
  - border-radius on submit or input. 999px and 10px are therefore probably ignored [A], so the live button shape may not match D8 (radius 9).
  - submit font-weight 600. AWS documents only bold/italic/normal, so 600 may be ignored [A].
  - outline-offset on input:focus. The focus outline is documented as "width in px", so 3px (F5) is possible within classic; offset is not.
  - The live check reported primary RGB 176/79/44 with white text (docs/verification.md:395), so the colours did apply.
- Colours: no mismatch with current tokens [V:read]. If the owner later changes any action/loss/muted token, cognito.css must be updated by hand (no generator or test links them).
- [R] Add a node test that asserts each cognito.css hex equals the named token value. It is read-only against web/branding and makes no AWS change, so drift becomes visible. This counts as a repo test, not a Cognito change, but rule 3 lists web/branding/* as never-change, so the owner must still OK it as "touching" that area (read-only).

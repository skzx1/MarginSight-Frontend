# MarginSight Frontend → Backend handoff

Audit date: 18 October 2026 (Asia/Bangkok). This report describes the checked-out frontend and uses the sibling backend implementation plus the repositories' dated verification notes to distinguish implemented API behavior from browser-only or synthetic behavior. A wired call is not by itself proof of a complete authenticated production workflow. Where the docs report deployment/smoke results, their exact scope is stated. Anything not established by source or recorded evidence is marked **unverified**.

Frontend scope: `web/src/app`, `web/src/lib`, `web/public`, and `docs/`. API availability cross-check: sibling `margin-sight-be/backend/src/api.ts`, its schemas/workers, and `margin-sight-be/docs/{status,verification,data-contracts}.md`. Backend ownership and generated formula rules are documented in `AGENT.md` and `docs/repository-split.md`.

Route map: the static public landing is `/` (`web/src/app/page.tsx`); login, onboarding, and the authenticated workspace are hosted at `/login/` (`web/src/app/login/page.tsx`). Workspace screens are client-side hash routes such as `#overview`, `#products`, `#finance`, `#assistant`, `#imports`, and `#reconciliation`, enumerated by `web/src/app/components/shell.tsx`; there are no frontend API route handlers because this is a static export (`AGENT.md`, `web/AGENTS.md`).

## 2. Backend work required

Existing financial formula, ledger, tenant checks, import/OCR workers, and several routes are already backend-owned. Do not reimplement those formulas in the frontend or create duplicate API resources. The formula artifact in `web/src/lib/domain.generated.js` is generated from the backend contract; repository rules require backend changes to be exported/synced and hash-verified (`AGENT.md`, `docs/repository-split.md`).

### 2.1 Finance API and expenses — required for real-store Finance

The current API gives monthly dashboard snapshots, not the finance-shaped dataset this screen needs. Suggested additions (or equivalent compatible extensions):

| Method + path | Purpose, request | Response fields |
|---|---|---|
| `GET /stores/{storeId}/finance?start=YYYY-MM-DD&end=YYYY-MM-DD&channel=all\|{platform}&compare=previous` | Return one consistent aggregate for the current Finance filters. Validate `start <= end`, bounded range, canonical platform IDs, and store membership. | `store, period:{start,end}, channel, currency:'THB', scope, dataOrigin, coverage:{orders,complete,incomplete,missingCost}, kpis:{revenueSatang,profitSatang,marginPct,totalCostsSatang,orders,averageSatang}, pnl:{grossSatang,reductionsSatang,netRevenueSatang,cogsSatang,feesSatang,shippingSatang,adsSatang,packagingSatang,otherSatang,profitSatang,marginPct}, daily:[{date,revenueSatang,costSatang,profitSatang,marginPct,orderCount}], channels:[{platform,revenueSatang,profitSatang,marginPct,sharePct,orderCount}], products:[{sku,name,revenueSatang,costSatang,feesSatang,profitSatang,marginPct,orderCount}], orders:{items:[...],next}, comparison:{period,values}|null`. Preserve unknowns as `null` plus `missingFields`; never coerce unknown to 0. |
| `GET /stores/{storeId}/expenses?start=...&end=...&channel=...&cursor=...` | Read expense entries used in finance totals. | `{items:[{id,category,amountSatang,occurredAt,channel,note,sourceRef,createdBy,createdAt}],next}` |
| `POST /stores/{storeId}/expenses` | Persist a merchant expense. Request: `{category,amountSatang,occurredAt,channel,note?,sourceRef?}`; amount is positive integer satang, date valid Bangkok business date, channel canonical, note bounded. | Created expense including server id, `store`, `dataOrigin:'REAL'`, creator and timestamps. Reject malformed/over-limit/foreign-store requests; deduplicate by an idempotency key if client retries. |
| `GET /stores/{storeId}/reports/export?type=finance&start=...&end=...&channel=...&format=csv\|xlsx` (or extend existing `/reports/export`) | Export the same server-calculated scope, not only the loaded rows in the browser. | `{downloadUrl,rows,store,period,channel,scope,expiresAt}`; apply formula-injection escaping and private-store URL controls. |

Business logic must use the canonical calculation/ledger snapshot and keep the documented scope: item revenue less product COGS, confirmed/posted platform fees, seller shipping, ads, packaging and explicitly recorded expenses, with unknown components preventing a “complete” profit. Existing engine semantics include integer satang, cost effective dates, actual-vs-estimated fee state, VAT/rules, unmapped cash deductions, returns and per-order allocation (`docs/calculation-policy.md`, `docs/data-contracts.md`). Finance must not subtract an expense twice if it is already represented on an order. Compute equal-duration previous-period comparison server-side (including cross-month bounds); do not compare calendar month to an arbitrary range. Reconcile P&L/channel/day/product totals at satang precision.

Validation/errors implied by UI: invalid/reversed/out-of-range dates; unknown channel/category; non-integer, negative, zero, overflow, or >THB1bn amounts (the browser's local-store validator caps at 100,000,000,000 satang); inaccessible store; stale cursor; duplicate retry; malformed/oversized note; incomplete underlying ledger; storage or worker failure. The UI currently has no server contract for how corrections/deletion or duplicate expense submission behave; define it before enabling the real-store form.

### 2.2 Persist store settings and notifications

Suggested contract (currently no settings fetch/save call):

| Method + path | Purpose, request | Response |
|---|---|---|
| `GET /stores/{storeId}/settings` | Load store-owned profile/preferences after membership authorization. | `{store,storeName,category,currency,reportingCycle,language,marginThreshold,email,dailyDigest,weeklyDigest,version,updatedAt}` |
| `PUT /stores/{storeId}/settings` | Save the same validated fields with optional `expectedVersion` for optimistic concurrency. | Saved canonical document/version. Use `409 SETTINGS_CHANGED` on stale version. |

Fields and existing frontend validation are specified in `web/src/lib/store-settings.ts`: name ≤120 chars, category enum, currency THB/USD/CNY, reportingCycle monthly/weekly/daily, language th/en, threshold 0–100, email ≤254 and valid if supplied; email is required if a digest is enabled. Decide whether storeName is a server profile mutation or a display-only preference (the current screen explicitly treats it as display-only); avoid silently changing the existing store name during migration.

Threshold evaluation, recipient verification/consent, send windows, timezone, unsubscribe, retries, bounce/suppression, and idempotent daily/weekly scheduling must be server-side before the UI claims delivery. The frontend currently only saves booleans and email locally and explicitly says it sends nothing (`web/src/app/components/store-settings.tsx`). Build notification jobs/provider integration only when those controls are enabled. Surface per-field validation and delivery status; never report “saved” until the server accepts it.

### 2.3 Assistant answers and cross-device chat history

The current `POST /stores/{storeId}/assistant` is already present for scenario requests. Keep numeric claims tied to canonical engine tools; accept only bounded message/context, validate SKU and month/store membership, enforce rate/token/tool limits, and return `{answer,provider,reason,result,comparison?}` with source/status. Current UI only calls it for questions matching a scenario keyword; ordinary recorded-data questions are assembled in `web/src/lib/assistant-service.ts` from `/dashboard` results and browser-side summaries. To make the assistant consistently server-owned, extend the existing endpoint (do not create a duplicate assistant endpoint) with optional `{start,end,channel,locale}` and return answer plus evidence/scope/coverage. If those general queries remain local templates by product decision, preserve that status and its 50-result limitation explicitly.

Sessions are browser-only. If history should sync to a user's other device, add store/account-scoped CRUD and message persistence, for example:

| Method + path | Purpose, request | Response |
|---|---|---|
| `GET /stores/{storeId}/assistant/sessions?cursor=...` | List history metadata. | `{items:[{id,title,createdAt,updatedAt,turnCount,context}],next}` |
| `POST /stores/{storeId}/assistant/sessions` | Create session; request `{title?,context:{start,end,sku?}}`. | Created session with server id and validated context. |
| `GET /stores/{storeId}/assistant/sessions/{sessionId}` | Load turns and draft if drafts are intentionally synced. | `{id,title,context,turns:[{id,question,createdAt,context,answer,result,evidence,state}],updatedAt}` |
| `POST /stores/{storeId}/assistant/sessions/{sessionId}/messages` | Persist question and invoke the existing assistant flow; request `{question,context,locale,idempotencyKey}`. | Persisted user turn + response/evidence/provider/fallback reason. Never accept client-supplied financial answers as truth. |
| `PATCH /stores/{storeId}/assistant/sessions/{sessionId}` | Rename/title or update context with version. | Updated session/version; `409` for stale edits. |
| `DELETE /stores/{storeId}/assistant/sessions/{sessionId}` | Delete one session/history. | `{deleted:true}`; scoped to its owner/store. |

If the static frontend's request helper remains limited to GET/POST, either use POST action routes consistently or extend `web/src/lib/auth.ts` to support PATCH/DELETE. Define retention, export/deletion, size limits (the current browser archive allows 100 sessions, 200 turns/session, 1,500-char question/draft), and handling for an in-flight answer after the client closes.

### 2.4 Existing real workflows: preserve contracts and close verification gaps

These are already implemented in the backend; the handoff is about end-to-end verification/adapter gaps, not rebuilding them:

- **Catalog and costs:** `GET /stores/{storeId}/products?cursor=...` returns `{items,next}`; `POST /stores/{storeId}/products` accepts `{sku,name,unit}`; `POST /stores/{storeId}/products/{sku}/cost-versions` accepts a confirmed cost/version payload. Keep SKU unique, unit consistency, positive/valid amounts, effective dates, immutable corrections, origin/source, actor, and idempotent retry (`web/src/lib/catalog-actions.ts`, `docs/data-contracts.md`, `margin-sight-be/backend/src/api.ts`). Add persistent selling price/quantity only if the product contract and UI actually need these as maintained records; the current UI labels them draft/unsaved.
- **Reports import:** Existing flow: `POST /stores/{storeId}/imports` `{kind,fileName,adapter,dataOrigin,acknowledgeOwnership?}` → presigned `PUT uploadUrl` → `POST /imports/{jobId}/complete`; poll `GET /jobs`, inspect `GET /imports/{jobId}`, `POST /imports/{jobId}/retry`, `POST /imports/{jobId}/review` `{acknowledgeExcludedRows:true,reason}`; list/resolve `GET /conflicts`, `POST /conflicts/{conflictId}/resolve` `{choice:'KEEP_EXISTING'|'USE_INCOMING',reason}`. API/worker already handles dedupe, conflicts, PARTIAL review, row errors, idempotent chunks and 5 MB/1,000-row file limits. For real platform use, obtain authorized samples/schema and implement verified adapters; `merchant-v1` is the current manual canonical format, while `mock-v1` is synthetic only (`docs/data-contracts.md`, `margin-sight-be/backend/src/importer.ts`, `margin-sight-be/docs/verification.md`).
- **Receipts:** Existing flow: `POST /receipts` `{fileName,dataOrigin}` → private presigned `PUT` → `POST /receipts/{id}/complete`; `GET /jobs`, `GET /receipts/{id}`; `POST /receipts/{id}/confirm` with `{effectiveFrom,acknowledgeTotals:true,items:[{sku,quantity,unitsPerPack,lineTotalTHB}]}`. Backend OCR/queue exists. Before “real use,” validate with consented Thai receipts and ground truth, improve item/unit extraction and manual-review recovery; current one-image synthetic AWS evidence failed product name/unit (`docs/verification.md`). Respect JPEG/PNG, 3 MB/20MP and receipt quotas documented in `docs/usage.md`/`docs/cost-log.md`.
- **Orders and confirmations:** Existing `GET /orders?month=...&cursor=...`, `GET /orders/{opaqueKey}/calculation`, and `POST /orders/{opaqueKey}/settle` `{confirmAllFeeLines:true,expectedInputHash,payoutSatang?}`. Reject stale hash (`409 ORDER_CHANGED_REVIEW_AGAIN`), require fee evidence, and re-open confirmation when ledger changes. These protections belong to API/domain, not client state (`web/src/app/screens/orders.tsx`, `margin-sight-be/backend/src/api.ts`, `docs/data-contracts.md`).
- **Rules and enrollments:** Existing `GET/POST /fee-rules` and `GET/POST /enrollments`. Validate effective windows, source references, rate caps, VAT state and status; “verified for estimate” must not imply platform-confirmed actual charges. `docs/assistant-marketplace.md` says `GET /assistant-options` and `POST /assistant-scenarios` are available, but neither route appears in the checked `margin-sight-be/backend/src/api.ts`, and the frontend's `MarketplaceControls`/`marketplaceRequest` are unused by `assistant.tsx`. This is a source/docs discrepancy, not evidence that an API is live. If this advertised scenario flow remains in scope, the backend needs the following routes and the frontend must wire them:

  - `GET /stores/{storeId}/assistant-options?month=YYYY-MM&sku={sku}` → `{version,reviewedAt,platforms:[{id,name,categories:[{id,name}],campaigns:[{id,name,sourceUrl,note,effectiveFrom}]}]}`. Scope options to supported products/platforms and effective dates; do not fabricate default/verified rates.
  - `POST /stores/{storeId}/assistant-scenarios` request `{month,sku,platform,category,sellerType,campaigns,commissionRateBps,commissionVat,paymentRateBps,paymentBase,buyerShippingSatang,fixedFeeExempt,growthTier,primeElectronicsRateBps?,liveRateBps?,confirmed:true}` → `{baseline,scenario,breakEven,sourceOrder,assumptions,missingFields,notSaved:true}`. Validate campaign IDs against the options version, exclusivity (e.g. mutually exclusive TikTok campaigns), numeric ranges, VAT/unknown semantics, one-SKU source order, input confirmation, and store membership. Return no profit when an essential rate is unknown. This route is a hypothetical estimate only; never mutate enrollment or order ledger.
- **Settlement reconciliation/export:** Existing `GET /reconciliation?month=...` and `GET /reports/export?month=...&format=csv|xlsx`; export responds with a private download URL. This is item settlement/fee evidence only, not whole-bank payout or physical inventory receipt (`web/src/app/screens/orders.tsx`, `web/src/lib/types.ts`, `margin-sight-be/backend/src/api.ts`).
- **LINE:** Existing `GET /integrations`, `POST /line/link`; webhook signature verification, expiring one-use code, queue handling and reply handler exist in backend. Configure/authorize secrets, enable the event mapping, test actual link/reply/unlink lifecycle and rate/usage limits. Current docs mark live LINE blocked without channel credentials (`docs/status.md`, `docs/demo.md`, `margin-sight-be/backend/src/line.ts`). No additional frontend endpoint is justified until unlink/status-refresh behavior is designed.

### 2.5 Native marketplace adapters

The app currently has no user-facing connect/sync control and backend reports `platform.status:'NOT_CONNECTED'`; no new connect endpoints are required to support today's manual canonical import flow (`web/src/app/screens/store.tsx`, `margin-sight-be/backend/src/api.ts`, `docs/data-contracts.md`). To turn marketing's multi-channel source list into automatic sync, backend work is **unverified/blocked on authorized platform access and sample schemas**: implement only adapters for approved sources, persist connection status/source cursor/consent, map platform order and fee statements into canonical ledger, and expose a status/sync route once frontend controls exist. Do not label manual uploads or mock rows as a live connection.

## 4. Cross-cutting backend requirements

- **Authentication and sessions:** Cognito OAuth code flow uses PKCE; browser stores the access token in `sessionStorage` and sends `Authorization: Bearer` (`web/src/lib/auth.ts`). API must validate issuer, audience/client, scopes, expiry and signature; accept access tokens, not trust IDs or tenant claims supplied by UI. Expired 401 clears local token. Cognito callback remains the origin root then redirects to `/login/` (`web/src/app/auth-callback.tsx`, `docs/welcome.md`).
- **Tenant separation and permissions:** Resolve subject from verified token. Derive store access from server membership for every read/write/job/download/link/export; reject cross-store IDs/cursors and guest tokens on normal routes. `POST /me/store` accepts only name and creates one personal empty store per subject; client must never choose owner/store ID (`docs/data-contracts.md`, `margin-sight-be/backend/src/api.ts`). The Frontend does not expose roles/invites; supported role behaviors beyond owner/member access are **unverified**.
- **Demo isolation:** Guest demo uses a separate capability in `sessionStorage`, routes through `/demo/api`, and is restricted to MOCK data, session/store scope, expiry and quotas. Docs describe 3 imports and 3 combined assistant/receipt requests per session plus daily caps (`web/src/lib/auth.ts`, `docs/demo.md`). Keep guest route authorization/provenance checks and TTL; do not use it as real-account verification.
- **Files and storage:** Browser asks API for an upload URL, PUTs directly, then calls complete; server chooses store-prefixed object key, validates object metadata/size/content, checks ownership and issues short-lived private download links (`web/src/lib/auth.ts`, `web/src/app/screens/imports.tsx`, `web/src/app/screens/receipts.tsx`, `docs/data-contracts.md`). Keep source files private and lifecycle/retention explicit. File limits currently surfaced: CSV/XLSX 5 MB, up to 1,000 rows; image 3 MB and 20 MP (UI also checks 20 MP).
- **Quotas and rate limits:** Enforce at API/worker side, including failed attempts and retries; UI counters are explanatory only. `docs/usage.md`, `docs/demo.md`, and `docs/cost-log.md` describe prototype limits (real store: 50 imports/store/day, 20 receipt reads/store/day, 30 AI requests/store/day, assistant output/tool limits; guest has stricter session/global limits). Do not infer commercial plan quotas from landing-page `[TBD]` or “3 per round” demo copy.
- **Audit trail:** Preserve source file/ref, adapter, data origin, import/job IDs, row errors/exclusions, duplicate/conflict decisions, review reason/actor/time, cost/rule versions, input hash/formula version, fee confirmation and receipt confirmation. Current import conflict and fee-confirm flows already rely on actor/reason/hash semantics (`docs/data-contracts.md`, `web/src/app/screens/imports.tsx`, `web/src/app/screens/orders.tsx`). Add comparable actor/version trail for expense/settings/session deletion.
- **Timezone and currency:** Persist UTC instants and integer satang/THB; use Asia/Bangkok for day/month boundaries, periods, expense dates and scheduled notices. Thai locale display may use Buddhist Era year; explicitly test API dates remain ISO Gregorian and never mix display year with stored year. Current frontend amount formatter divides satang by 100 and settings currency selector does not convert values (`web/src/lib/format.ts`, `web/src/lib/overview-data.ts`, `web/src/lib/store-settings.ts`).
- **PDPA/privacy:** Define purpose/consent for sales, receipts, AI prompts, email and LINE; data retention/deletion by tenant and guest TTL; export/access/correction/deletion process; vendor/region disclosures (receipt source notes mention storage/processing regions in `docs/verification.md`); redact tokens, emails, uploaded contents and AI prompts from logs; encrypt private objects and restrict roles; document subprocessors and incident contact. These policy/retention details are not complete in the landing content (`web/src/app/welcome/content.ts`).
- **Errors and idempotency:** Return stable error codes/field paths the frontend can display; preserve HTTP statuses (401 expiry, 403 tenant, 404 unknown record, 409 conflict/stale hash, 413 file/range, 429 quota, 5xx retryable). Require idempotency for create/upload-complete/import chunks/OCR confirm/expense create/assistant turn to prevent duplicate writes after network retries. Preserve current `REQUEST_FAILED` / error object shape in `web/src/lib/auth.ts` or update UI mapping with the API contract.
- **Static frontend constraint:** This is Next static export; API work belongs in backend functions, not Next server routes (`AGENT.md`, `web/AGENTS.md`). Config in `/config.json` and `NEXT_PUBLIC_*` is public only (`web/src/lib/auth.ts`, `.env.example`).

## 5. Hidden assumptions and risks

1. **50-order detail ceiling leaks into summaries.** Backend `/dashboard` returns top-level full-month aggregates but only the latest 50 `results` (`margin-sight-be/backend/src/api.ts`, `margin-sight-be/docs/verification.md`). Overview/Finance/assistant client paths consume `results` and aggregate them in browser (`web/src/lib/use-overview-dashboard.ts`, `web/src/app/screens/overview.tsx`, `web/src/app/screens/finance.tsx`, `web/src/lib/assistant-service.ts`). A populated month can therefore have correct API totals and incomplete client-built breakdowns/rankings; paginated or aggregate endpoints are needed.
2. **Finance is a separate fabricated dataset in demo, and partially reconstructed in real mode.** 310 demo orders are generated in `web/src/lib/finance-mock.ts`; real calculations do not contain gross/reductions or commerce fulfillment status, and `fromCalculation` explicitly sets `grossSatang/reductionsSatang` null and `commerceStatus:'UNKNOWN'` (`web/src/lib/finance-data.ts`). Do not read demo rows as sales. Add response fields/API contract before claiming gross-vs-net or completed/pending/returned counts for real stores.
3. **Expense totals may duplicate costs.** Real expense writes are disabled today, but Finance sums all browser-local expense entries and subtracts them from profit while adding category totals (`web/src/lib/finance-data.ts`, `web/src/app/screens/finance.tsx`). On server migration, define whether an expense is incremental vs already represented in an order cost/fee line, and support source/reference/reconciliation to prevent double deduction.
4. **Catalog commercial fields are transient.** Product CSV/manual forms collect price and quantity, then add them only to browser state; API product schema shown by current contract stores SKU/name/unit and cost versions (`web/src/app/components/product-csv-import.tsx`, `web/src/lib/catalog-actions.ts`, `docs/data-contracts.md`). Reload may remove those display values. Product “profit” is a simple price-minus-cost preview with fees excluded (`web/src/lib/catalog-actions.ts`), not the canonical net profit calculation.
5. **Settings save can look like a server change.** Profile, category, currency, fiscal period, alert threshold, and notification preferences are saved in localStorage; store-name hint says it does not change server name and currency does not convert money (`web/src/app/components/store-settings.tsx`, `web/src/lib/store-settings.ts`). Migration needs explicit treatment of old local values, conflict policy and honest save feedback.
6. **Assistant chat history is not in the API.** Account/store hash scopes a localStorage key but provides no data protection or cross-device sync (`web/src/lib/assistant-sessions.ts`). History can contain prompts/results; define retention, account logout behavior, cross-tab updates and deletion before moving it server-side.
7. **“AI assistant” includes non-AI answer paths.** Only scenario-tagged requests call `/assistant`; normal profit/product answers use `GET /dashboard` plus frontend keyword heuristics, templates and `summarizeOrders` (`web/src/lib/assistant-service.ts`). These are bounded by returned result pages and can diverge from a server aggregate.
8. **Platform/channel IDs need a single enum.** Frontend mock finance uses `TikTok`, Overview options include `TikTok`, user-facing copy says `TikTok Shop`, and imported `platform` is a free string in canonical data (`web/src/lib/finance-data.ts`, `web/src/lib/finance-mock.ts`, `web/src/lib/overview-data.ts`, `docs/data-contracts.md`). Exact string filtering can split one channel into multiple rows; canonicalize IDs/labels server-side and return stable IDs.
9. **Settlement language can be overread.** The route checks item-fee/payout evidence only and explicitly excludes full bank deposits (`web/src/app/screens/orders.tsx`, `web/src/lib/copy.ts`, `margin-sight-be/backend/src/api.ts`). No physical goods-receipt feature was found; do not treat “ตรวจยอดรับสินค้า” as stock receiving.
10. **Native platform/OCR/LINE confidence is limited by evidence.** Platform integration currently says NOT_CONNECTED; native export mappings lack authorized sample schemas; OCR synthetic example misread name/unit; LINE credentials/live flow are external blockers (`margin-sight-be/backend/src/api.ts`, `docs/data-contracts.md`, `margin-sight-be/docs/verification.md`, `docs/status.md`).
11. **External account isolation remains incompletely verified.** Backend code and tests enforce membership, and demo tests deny cross-store access; however, latest status explicitly says full AWS two-user/two-store authenticated workflow is not complete (`margin-sight-be/backend/src/auth.ts`, `margin-sight-be/backend/src/api.ts`, `margin-sight-be/docs/status.md`). A local/unit test is not a substitute for the live acceptance run.
12. **Landing claims are intentionally provisional.** “Free” tier and premium price/limits, contact, privacy, and terms are incomplete `[TBD]`; no testimonials or customer counts are present (`web/src/app/welcome/content.ts`, `docs/welcome.md`). Resolve before public acquisition or paid conversion.
